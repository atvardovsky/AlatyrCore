# Alatyr Release Migration Report

This reviewed report compares `v0.1.0-alpha.3` with the source tree prepared
for `0.1.0-alpha.4`. It is source evidence, not approval to modify a target
repository.

Report ID: `alatyr-0.1.0-alpha.4`
Prepared by: `AlatyrCore maintainers`
Prepared at: `2026-08-02`

## Version Scope

From manifest: `v0.1.0-alpha.3:framework/rule-registry.json`
To manifest: `framework/rule-registry.json`
From framework version: `0.1.0-alpha.3`
To framework version: `0.1.0-alpha.4`
From adapter schema version: `2`
To adapter schema version: `3`
From template version: `3`
To template version: `4`

## Adapter Contract Impact

- Framework, adapter schema, template, rule registry, rule ownership, and
  target template surfaces changed.
- `ALATYR-DIAGRAM-001`, `ALATYR-OPERATION-001`, and `ALATYR-TEAM-001` were
  added; `ALATYR-ADAPTER-001` changed.
- Context routing now uses a compact schema-3 index and lazy profile, intent,
  migration, consistency, and task-scale descriptors.
- Scaffold output is projected to the selected `core`, `standard`, or `full`
  support profile and records that profile in `.ai/alatyr.yaml`.
- Assistant capability evidence is split into a generated index and one
  freshness-aware record per supported assistant surface.
- Operation and capability indexes are derived from canonical records.
- Diagram conformance can validate captured client results, not only prepared
  prompts.

## Required Target Actions

- Run `recheck-after-framework-update` against this release.
- Compare the installed framework baseline with changed source framework
  files before applying updates.
- Migrate `.ai/alatyr.yaml` to adapter schema `3`, record the selected support
  profile, and migrate the target template baseline to version `4`.
- Replace an inline context-router profile corpus with the compact schema-3
  router and the profile-specific descriptor files selected for the adapter.
- Reconcile the operation index with the canonical operation catalog.
- When diagram discussion is enabled, create the capability index and the
  installed assistant surface records; reverify stale or expired claims.
- Run the target adapter validator and target-specific checks, or record each
  unavailable check and its residual risk.
- Obtain target approval before overwriting existing assistant instructions,
  local deviations, or other protected adapter surfaces.

## Optional Target Actions

- Select `core` or `standard` support where full team, diagram, or AI
  infrastructure modules are unnecessary.
- Capture real diagram result evidence for supported assistant clients.
- Rebaseline context-cost evidence after project-specific bootstrap facts are
  resolved.

## Validation Run

Source validation: `python3 tools/check_all.py` and `git diff --check` are
required before tagging.
Target validation: run the portable target validator with the target's

## Residual Risks

- Source comparison cannot see target-local deviations or prove target
  business facts.
- Profile projection prevents contradictory scaffold claims but still
  requires target evidence to replace placeholders.
- Capability records describe observed client behavior; client updates can
  invalidate them and trigger reverification.
- Logical integrity and project invariant review remain assistant and human
  reasoning responsibilities even when structural checks pass.
