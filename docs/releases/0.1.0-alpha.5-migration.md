# Alatyr Release Migration Report

This reviewed report compares source commit `f5b4974` prepared as
`0.1.0-alpha.4` with the source tree prepared for `0.1.0-alpha.5`. It is
source evidence, not approval to modify a target repository.

Report ID: `alatyr-0.1.0-alpha.5`
Prepared by: `AlatyrCore maintainers`
Prepared at: `2026-08-06`

## Adapter Contract Impact

- Framework, adapter schema, template, rule registry, rule ownership, target
  template, installer, and validator surfaces changed.
- `ALATYR-PACKAGE-001` and the `PACKAGE` rule-owner category were added.
- `ALATYR-APPROVAL-001`, `ALATYR-CHANGE-001`,
  `ALATYR-INTEGRITY-001`, `ALATYR-CONTEXT-001`, `ALATYR-MODULE-001`,
  `ALATYR-LIFECYCLE-001`, and `ALATYR-EVIDENCE-001` changed.
- The machine approval record advanced from schema 1 to schema 2. Schema 1
  remains readable for legacy path-scope validation, but activated change
  packages require schema-2 semantic fields for strict package enforcement.
- The optional `change-packages` module adds a lazy overlay, compact index,
  machine record, redacted report, flow, installer/update contracts, and
  explicit target-validator selection.

## Required Target Actions

- Run `recheck-after-framework-update` against this release.
- Migrate `.ai/alatyr.yaml` to adapter schema `4` and target template version
  `5` after reviewing target-local deviations and approval requirements.
- Migrate machine approval record creation to schema 2 for new protected work.
  Preserve legacy records as historical evidence.
- If `change-packages` is enabled, add the empty compact index, lazy overlay,
  flow, machine record, redacted report, module/manifest entries, target
  ownership, retention/redaction policy, and validator invocation.
- Preserve existing target package, approval, plan, discussion, and operation
  records. Do not replace them with source placeholders.
- Recheck product-change and large-task flows so package activation remains
  separate from ordinary local work and from large-task activation.
- Run the target adapter validator and target-specific validation, or record
  each unavailable check and residual risk.
- Obtain target approval before overwriting existing assistant instructions,
  local deviations, approval policy, or protected adapter surfaces.

## Optional Target Actions

- Keep `change-packages` deferred or disabled when the target does not need
  coherent material-change, audit, pilot, or publication evidence.
- For public cases, use a dedicated branch or worktree and a reviewable Git
  range or pull request.
- Capture a redacted Markdown report only when human review or publication
  needs it; keep raw conversations outside package evidence by default.

## Residual Risks

- Structural validation cannot infer missing domain invariants, undeclared
  semantic effects, or accepted architecture.
- Selected-file snapshots remain bounded evidence and cannot prove a complete
  public before-to-after change set.
- Git and pull-request provenance still require maintainers to confirm that
  the declared package contains the intended coherent outcome.
- Target retention, privacy, redaction, and approval policy cannot be inferred
  from AlatyrCore templates.
