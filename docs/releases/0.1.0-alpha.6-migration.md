# Alatyr Release Migration Report

This reviewed report compares source commit `5e2fb91` prepared as
`0.1.0-alpha.5` with the source tree prepared for `0.1.0-alpha.6`. It is source
evidence, not approval to modify a target repository.

Report ID: `alatyr-0.1.0-alpha.6`
Prepared by: `AlatyrCore maintainers`
Prepared at: `2026-08-07`

## Adapter Contract Impact

- Framework, adapter schema, template, rule registry, rule ownership, target
  template, installer, routing, operation, validator, scaffold, and conformance
  surfaces changed.
- `ALATYR-CODEDOC-001` and the `CODEDOC` rule-owner category were added.
- `ALATYR-CONTEXT-001`, `ALATYR-SOURCE-001`,
  `ALATYR-INTEGRITY-001`, `ALATYR-ADAPTER-001`, `ALATYR-MODULE-001`,
  `ALATYR-OPERATION-001`, `ALATYR-LIFECYCLE-001`, and
  `ALATYR-EVIDENCE-001` changed.
- The optional `code-documentation` module adds a compact project index and
  catalog, multiple source-set profiles, a lazy intent route, profile-review
  report, target-adapted skill, documentation-sync modes and aliases,
  generated-output policies, and source/target structural validation.
- Routine bootstrap does not load code-documentation detail. Static source
  measurement records 1,619 bootstrap words and a 68.4% reduction between the
  compact code-documentation route and its full reference union.

## Required Target Actions

- Run `recheck-after-framework-update` against this release.
- Migrate `.ai/alatyr.yaml` to adapter schema `5` and target template version
  `6` after reviewing target-local deviations and approval requirements.
- Add `ALATYR-CODEDOC-001` and `framework/code-documentation.md` to the
  installed framework baseline even when the optional module remains deferred.
- Preserve existing project comment conventions, documentation generators,
  generated outputs, publication systems, CI jobs, skills, and ownership.
  Do not replace them with source placeholders or one universal style.
- If `code-documentation` is enabled, add and adapt the project documentation
  index, catalog, profiles, intent route, profile-review report,
  documentation-sync contract, target skill, manifest/module entries, gates,
  operation aliases, and target validator coverage.
- Resolve each enabled profile from target evidence. Record bounded source
  matches, language/framework, audience, visibility, comment syntax, semantic
  sections, canonical fact owners, generator/configuration, output policy,
  validation, owner, evidence revision, migration scope, and approval needs.
- Require at least one unambiguous accepted profile before claiming the module
  is enabled. Keep other profiles proposed, deprecated, contradicted, unknown,
  deferred, or blocked as target evidence requires.
- Keep generated reference documentation derived and prohibit direct edits.
  Select `ci-artifact`, `committed-generated`, `local-only`, or
  `external-publish` only from target policy.
- Run the target adapter validator and project-specific comment lint,
  generation, link, example, build, or manual review, or record each unavailable
  check and residual risk.
- Obtain target approval before adding dependencies, changing CI, publishing
  externally, accepting a profile, broadly rewriting source comments, or
  overwriting existing assistant infrastructure.

## Optional Target Actions

- Keep `code-documentation` deferred or disabled when the target does not need
  generated reference documentation or cannot maintain profile ownership.
- Start with one bounded high-value public source set instead of migrating the
  entire repository.
- Use different accepted profiles for frontend, backend, shared-library, or
  infrastructure areas when target evidence justifies the difference.
- Adapt the target skill only after profiles are accepted; assistant-native
  wrappers remain optional and should point to the canonical target profiles.
- Prefer existing language-native or ecosystem tooling before introducing a
  new generator.

## Residual Risks

- Structural validation cannot prove that a comment is true, useful, complete,
  or aligned with unrecorded project intent.
- Generator success cannot prove business, architecture, security, API, data,
  or operational correctness.
- Path/source-set matching cannot resolve semantic profile overlap that the
  target has not represented explicitly.
- Existing project documentation conventions, dependency constraints, CI,
  publication systems, and maintenance capacity cannot be inferred from source
  templates.
- Assistant-native skill loading still differs by client; canonical operation
  routing and bridge pointers remain the portable baseline.
