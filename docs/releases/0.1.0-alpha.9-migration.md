## Adapter Contract Impact

- Framework, adapter schema, template, rule registry, rule ownership, target
  template, installer, routing, operation, validator, scaffold, bridge, and
  conformance surfaces changed.
- No rule IDs were added or removed. `ALATYR-TEAM-001`,
  `ALATYR-CONTEXT-001`, `ALATYR-SOURCE-001`, `ALATYR-ADAPTER-001`,
  `ALATYR-OPERATION-001`, `ALATYR-BRIDGE-001`, `ALATYR-EXTENSION-001`,
  `ALATYR-LIFECYCLE-001`, and `ALATYR-EVIDENCE-001` changed.
- Team-enabled targets move from one schema-1 registry containing actors and
  tasks to a schema-2 model: target-owned policy, registry metadata, per-task
  records, generated active-work index, backend contract, and ignored local
  identity.
- State-changing operations run a compact active-work preflight. Full team
  context remains lazy and is loaded only for a relevant match or unresolved
  coordination fact.
- Routine bootstrap is 1,899 words. Static source measurement records a 92.8%
  reduction between the 796-word compact team route and the 11,123-word full
  team reference union. The combined large-task and team overlays are 2,255
  words; framework-update routing retains an 85.9% static word reduction from
  the complete candidate union.

- Migrate `.ai/alatyr.yaml` to adapter schema `8` and target template version

- Keep team collaboration deferred when it is not enabled. Do not create actor
  or task facts merely because the new templates exist.
- For a team-enabled adapter, derive `.ai/project/team-policy.json` from target
  evidence and preserve its decision authority, priority, transition, review,
  identity-verification, storage, retention, and privacy rules.
- Convert each schema-1 embedded task to an independently updateable schema-2

  references, scope, claims, priorities, reviews, checkpoints, handoffs,

- Replace the old registry task array with schema-2 registry metadata and
  generate `.ai/assistant/team/active-work-index.json` from non-terminal task
  records. Perform conversion, index generation, validation, and registry
  switch as one planned operation; do not leave mixed authoritative schemas.
- Add and adapt `.ai/assistant/team/backend-contract.json`, the task record
  template, local identity example, identity flow, team skill, collaboration
  review, updated gate, operation routes, and source-of-truth entries.

  ignored. Local selection is attribution only and must not be treated as
  authentication, authority, or permission evidence.
- Resolve backend atomic-write, compare-and-swap, lease, consistency,
  availability, synchronization, and conflict behavior from target evidence.
  Do not claim external-provider guarantees that were not verified.
- Route provider-specific tracker or collaboration integrations through the

- Run the portable target adapter validator and target-selected tests or

- Obtain target approval before replacing canonical team policy, changing
  authority or transition rules, adding dependencies, changing permissions,

## Residual Risks

- Structural validation cannot authenticate an actor or prove that a selected
  identity represents the person operating the assistant.
- Repository files cannot provide atomic multi-writer updates without a
  compare-and-swap capable backend or repository workflow.
- Active-index parity proves agreement with inspected task records, not the
  truth or completeness of an external tracker.
- Backend declarations do not prove provider availability, permission safety,
  synchronization correctness, or conflict recovery.
- Assistant-native skill loading and preloaded instructions differ by client;
  canonical operation and context routing remain the portable baseline.
- Aggregate collaboration recommendations require target review and do not
  prove productivity, causality, or suitability of a proposed AI artifact.
