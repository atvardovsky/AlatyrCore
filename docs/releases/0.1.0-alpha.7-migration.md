# Alatyr Release Migration Report

This reviewed report compares source commit `7f533af` prepared as
`0.1.0-alpha.6` with the source tree prepared for `0.1.0-alpha.7`. It is source
evidence, not approval to modify a target repository.

Report ID: `alatyr-0.1.0-alpha.7`
Prepared by: `AlatyrCore maintainers`
Prepared at: `2026-08-07`

## Adapter Contract Impact

- Framework, adapter schema, template, rule registry, rule ownership, target
  template, installer, routing, operation, validator, scaffold, bridge, and
  conformance surfaces changed.
- `ALATYR-VOCABULARY-001` and the `VOCABULARY` rule-owner category were added.
- `ALATYR-CONTEXT-001`, `ALATYR-SOURCE-001`,
  `ALATYR-INTEGRITY-001`, `ALATYR-ARCHITECTURE-001`,
  `ALATYR-CODEDOC-001`, `ALATYR-ADAPTER-001`, `ALATYR-MODULE-001`,
  `ALATYR-OPERATION-001`, `ALATYR-BRIDGE-001`,
  `ALATYR-LIFECYCLE-001`, and `ALATYR-EVIDENCE-001` changed.
- The optional `project-vocabulary` module adds a compact catalog, scoped term
  records, data-dictionary links, a lazy intent, review report, adapted skill,
  conversational operation, help aliases, bridge routing, and structural
  validation.
- Routine bootstrap does not load vocabulary detail. Static source measurement
  records 1,693 bootstrap words and a 65.0% reduction between the compact
  vocabulary route and its full reference union.

## Required Target Actions

- Run `recheck-after-framework-update` against this release.
- Migrate `.ai/alatyr.yaml` to adapter schema `6` and target template version
  `7` after reviewing target-local deviations and approval requirements.
- Add `ALATYR-VOCABULARY-001` and `framework/project-vocabulary.md` to the
  installed framework baseline even when the optional module remains deferred.
- Preserve existing glossaries, acronym lists, terminology docs, data
  dictionaries, schemas, APIs, naming rules, accepted definitions, owners, and
  review processes. Do not replace them with source placeholders.
- If `project-vocabulary` is enabled, add and adapt the vocabulary index,
  compact catalog, full term records, data-dictionary links, intent route,
  vocabulary flow, term-review report, skill, manifest/module entries, gates,
  help aliases, bridge capability fields, and target validator coverage.
- Resolve catalog and term metadata from target evidence. Record stable IDs,
  canonical and normalized terms, aliases, acronyms, kind, domains, usage
  scopes, state, meaning, non-meanings, owner, decision authority, canonical
  sources, evidence revision, related terms, data links, validation, and gaps.
- Require at least one accepted term before claiming the module is enabled.
  Keep other terms observed, proposed, deprecated, contradicted, unknown,
  deferred, or blocked as target evidence requires.
- Keep distinct accepted meanings scoped by domain. Reject same-domain
  accepted lookup collisions until target owners resolve them.
- Keep data links directional and preserve canonical ownership of schemas,
  APIs, fields, events, units, enums, business rules, architecture, security,
  code, and operations.
- Run the target adapter validator and target vocabulary, link,
  documentation, schema, API, code, or manual review checks, or record each
  unavailable check and residual risk.
- Obtain target approval before accepting or deprecating semantic definitions,
  performing broad terminology replacement, or changing protected canonical
  owners and companion surfaces.

## Optional Target Actions

- Keep `project-vocabulary` deferred or disabled when the target has no stable
  terminology owner or cannot maintain accepted definitions.
- Start with high-value domain, product, architecture, operational, and
  acronym terms that repeatedly create ambiguity. Do not index every identifier.
- Link existing data dictionaries or schemas instead of copying their fields
  into vocabulary records.
- Adapt the target skill only after the module records and ownership model are
  accepted; assistant-native wrappers remain optional thin pointers.
- Add target-local fuzzy search only as candidate discovery. Exact catalog and
  scoped accepted-state resolution remain the authoritative lookup path.

## Residual Risks

- Structural validation cannot prove that a term definition, scope, owner,
  relationship, state, or acceptance decision is semantically correct.
- Existing target vocabulary and domain ambiguity cannot be inferred reliably
  from source templates or usage frequency.
- Exact normalized lookup cannot detect every semantic synonym or indirect
  contradiction; assistant and human review remain necessary.
- A stale vocabulary may normalize project wording incorrectly if ownership,
  evidence revision, and review triggers are not maintained.
- Assistant-native skill loading differs by client; canonical operation routing
  and compact catalog lookup remain the portable baseline.
