# Alatyr Release Migration Report

This reviewed report compares the nearest reachable tagged source baseline
`v0.1.0-alpha.3` with the source tree prepared for `0.1.0-alpha.12`.
Migration reports for intervening `0.1.0-alpha.4` through
`0.1.0-alpha.11` remain part of the evidence chain. This report is source
evidence, not approval to modify a target repository.

Report ID: `alatyr-0.1.0-alpha.12`
Prepared by: `AlatyrCore maintainers`
Prepared at: `2026-08-20`

## Adapter Contract Impact

- The complete framework pack adds `subagent-delegation.md` and rule
  `ALATYR-DELEGATION-001`.
- Target template version 12 adds a delegation policy, delegated-execution
  overlay, delegation flow, packet, bridge fields, and per-surface subagent
  capability fields.
- Adapter schema version 11 covers the optional delegation policy and
  per-assistant capability records. The manifest shape is unchanged, but an
  installed target must advance its recorded adapter schema only after these
  contracts are reconciled; file presence does not enable the module.
- Enabled targets require current assistant capability evidence, target-owned
  dispatch-backend and role/model bindings, bounded actions/context/tools/
  writes, fallback, privacy, validation, and primary-agent convergence.
- Native workers, approved external dispatchers, suggestion-only handoff, and
  unsupported/local fallback use one portable packet and convergence contract
  across all nine assistant surfaces. External dispatchers must resolve to
  target AI-infrastructure items rather than vendor assumptions.
- A documented product or model name is not installation evidence. Existing
  unsupported or unknown assistant surfaces remain valid when delegation is
  disabled, deferred, or suggestion-only under target policy.

## Migration Action Hints

- Install the new framework owner only through a compatible complete pack.
- Keep `subagent-delegation` disabled, deferred, not applicable, or blocked
  unless target evidence justifies and maintains it.
- When enabling it, adapt the policy and every supported assistant capability
  record from the actual client, subscription/access, native or external
  dispatch backend, tool, permission, and model-selection behavior.
- Preserve target role/model bindings, limits, privacy, fallback, and packet
  evidence during later updates. Never replace them with source placeholders.
- Keep the primary assistant responsible for project decisions, approvals,
  integration, logical integrity, and final validation.

## Required Target Actions

- Run `recheck-after-framework-update` against this release.
- Migrate `.ai/alatyr.yaml` to adapter schema `11` and target template version
  `12` after reviewing local deviations and protected adapter changes.
- Update the installed framework baseline only after the selected framework
  pack and adapter contracts have been reconciled.
- Reconcile the module catalog/profile and bridge capability records. Do not
  enable delegation automatically.
- If delegation is enabled, adapt and validate the policy, overlay, flow,
  packet, per-surface dispatch backend and capability evidence, external
  dispatcher item, role/model bindings, write/tool isolation, fallbacks,
  privacy, and primary convergence.
- Re-run target-owned validation and logical integrity review. Structural
  checks do not prove safe decomposition, model availability, semantic
  correctness, latency improvement, or cost reduction.

## Optional Target Actions

- Bind a fast focused worker to a currently available assistant model only
  after verifying that the selected client can launch subagents and select
  that model.
- Keep suggestion-only mode when the client cannot dispatch model-selected
  subagents but the team wants delegation recommendations.
- Capture comparable packet preparation, review, latency, validation, and
  rework evidence before making performance or cost claims.

## Residual Risks

- Assistant products expose different subagent and model-selection behavior;
  source templates cannot prove runtime parity or current account access.
- Fast models can reduce latency for bounded work but may increase rework or
  total cost when decomposition, review, or synchronization is poor.
- Static capability and packet checks cannot prove that a delegated task is
  semantically independent or that actual writes stayed isolated in an
  external client.
- Historical releases after `v0.1.0-alpha.3` have migration reports but no
  reachable tags; the evidence chain remains weaker than a tag for every
  release.

## Safety

This report does not enable subagents, select a paid model, modify a target
repository, grant permissions, approve protected changes, publish a tag or
release, or claim latency, quality, or cost improvement.
