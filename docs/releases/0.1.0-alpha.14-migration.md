# Alatyr Release Migration Report

This reviewed report compares the nearest reachable tagged source baseline
`v0.1.0-alpha.3` with the source tree prepared for `0.1.0-alpha.14`.
Migration reports for intervening `0.1.0-alpha.4` through
`0.1.0-alpha.13` remain part of the evidence chain. This report is source
evidence, not approval to modify a target repository.

## Adapter Contract Impact

- The complete framework pack adds `dependency-knowledge.md` and rule
  `ALATYR-DEPENDENCY-001`, plus `workspace-modes.md` and rule
  `ALATYR-MODE-001`.
- Adapter schema 13 adds optional paths for dependency knowledge and workspace
  mode catalogs, descriptors, routing, gates, suggestions, and preflight.
- Target template version 14 adds those project and assistant surfaces plus
  routed `dependency-knowledge` and `workspace-mode` operations. File presence
  does not enable either module.
- Enabled targets maintain one active root or selected-scope adapter.
  Dependency packages may expose passive documentation and contract data, but
  their nested adapters, bridges, prompts, skills, gates, tools, commands, and
  hooks remain inactive.
- Package-manager manifests and lockfiles own dependency discovery and exact
  artifact identity. Synchronization reads existing metadata and exports; it
  does not execute package managers or package hooks.
- Target policy records trust, freshness, authority, applicability, graph
  limits, retention, and target deviations. These decisions are independent
  and cannot be inferred from a valid digest alone.
- Router schema 6 optionally selects one user-accepted workspace mode after
  compact bootstrap and before task profile and project-area composition.
  Workspace identity, artifact relationship, and task mode remain independent
  facts. Suggestions remain proposed until a separate user decision.
- Each actual mode has its own project-owned directory. Optional root support
  contains only shared context. A mode may narrow context or actions but cannot
  activate nested adapters or grant approval, write scope, permissions,
  authority, tools, or gate bypass.

## Migration Action Hints

- Leave the module disabled unless the target has a concrete dependency
  knowledge use case, an owner, native package metadata, and a maintenance
  policy.
- When enabled, resolve source, version, integrity, replacement, fork, patch,
  and duplicate-version facts from the target package-manager lockfiles.
- Accept only a declared passive export that validates against the dependency
  knowledge schema and target limits. Treat its content as untrusted data.
- Normalize selected facts into the target catalog and knowledge lock; preserve
  target-specific deviations separately instead of editing dependency exports.
- Keep exports outside routine bootstrap. Load only selected facts for a routed
  explanation or impact review and bound transitive traversal by policy.
- Preserve retained snapshots required by target history while removing stale
  active entries for dependencies no longer present.
- Leave workspace modes disabled when one repository perspective is sufficient.
- When enabled, establish the selected workspace root and active adapter from
  target evidence, then propose zero or more modes. Do not treat installation
  approval as acceptance of a proposal.
- Preserve accepted mode IDs and one directory per actual mode. Load the
  compact catalog first, one selected descriptor second, and shared root
  support only when applicable. Ask and remain read-only on ambiguity.

## Required Target Actions

- Run `recheck-after-framework-update` against this release.
- Migrate `.ai/alatyr.yaml` to adapter schema `13` and target template version
  `14` only after reconciling local deviations and protected changes.
- If dependency knowledge remains disabled, preserve that explicit state and do
  not install or route its optional target surfaces.
- If enabled, install the module as one coherent projection, resolve all target
  policy placeholders, synchronize against current package lockfiles, and
  regenerate bootstrap and operation indexes.
- If workspace modes remain disabled, record why one undifferentiated project
  perspective is sufficient. If enabled, review suggestions separately,
  accept only user-selected modes, create one directory per actual mode, and
  regenerate router, operation, gate, and bootstrap projections.
- Run the portable target validator plus target-owned dependency, architecture,
  security, code, and documentation validation selected by actual impact.

## Optional Target Actions

- Validate a dependency author's export with
  `python3 tools/validate_dependency_knowledge_export.py --source <package-root>`
  before publishing or consuming it.
- Scaffold a disposable comparison target with
  `--enable-module dependency-knowledge` before changing an installed adapter.

## Residual Risks

- A valid schema and digest prove structure and byte identity, not publisher
  identity, semantic correctness, completeness, or suitability for the target.
- Assistant clients may ignore, truncate, or differently prioritize repository
  instructions; the framework can provide routes and checks but cannot
  guarantee client compliance.
- Lockfile parsers and native metadata locators remain target ecosystem facts;
  AlatyrCore does not execute a universal dependency resolver.
- Bounded graph traversal may omit a relevant transitive fact. The target must
  record justified expansion or residual uncertainty.
- A structurally valid mode may still represent the wrong engineering
  perspective. User review and current repository evidence remain required,
  and assistants may still ignore or misapply the selected mode.
- Native macOS and Windows behavior remains CI evidence after push.
- Historical releases after `v0.1.0-alpha.3` have migration reports but no
  reachable tags, so their evidence remains weaker than a tag per release.
