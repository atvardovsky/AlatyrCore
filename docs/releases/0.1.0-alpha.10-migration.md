## Adapter Contract Impact

- Framework, adapter schema, target template, context routing, manifest,
  framework-pack, registry, inventory, validator, scaffold, release, and source
  conformance contracts changed.
- No rule IDs were added or removed. `ALATYR-CONTEXT-001`,
  `ALATYR-ADAPTER-001`, `ALATYR-MODULE-001`, and
  `ALATYR-LIFECYCLE-001` changed.
- Target context-router schema 4 separates total, portable, and reserved target
  context budgets and adds checked representative cost scenarios. The routine
  bootstrap remains 1,899 words under its 1,900-word soft limit.
- The target manifest now records `framework.pack`. Existing installations
  that contain the complete portable corpus should migrate to `complete`;
  upgrade work must not delete framework files merely to select a smaller pack.
- New installations may pair `core`, `standard`, and `full` support profiles
  with dependency-closed `core`, `standard`, and `complete` framework packs.
  Selective packs carry projected rule-registry, ownership, and inventory
  evidence.
- Source checks now use a dependency-aware manifest, bounded parallelism, and
  explicit fast, full, change, and release profiles. These are source tooling
  contracts, not new target validation commands.

- Migrate `.ai/alatyr.yaml` to adapter schema `9` and target template version

  installation unless a separately reviewed migration deliberately selects a
  dependency-closed smaller pack.

  and reserved-target profile budgets and keep the compact bootstrap within its

  static routing evidence; do not present whitespace-word measurements as
  actual model-token or billing evidence.

  approval, and validation context even when it exceeds a soft budget, and
  record the expansion receipt.

  `framework/framework-packs.json`. Keep generated registry and ownership
  surfaces aligned with the selected pack.
- Run the portable target adapter validator and target-owned tests or manual
  reviews, or record each unavailable check and residual risk.
- Obtain target approval before overwriting canonical adapter instructions,
  changing enabled modules, shrinking an installed framework pack, or changing
  protected target behavior.

## Optional Target Actions

- Keep existing adapters on the `complete` pack. Pack reduction is optional
  and provides repository-surface reduction, not automatic per-task token
  savings; the context router remains responsible for load cost.
- Select `core` or `standard` only for a new or explicitly migrated adapter
  whose enabled modules fit that pack. Expand the pack before enabling an
  absent module owner.
- Use the target context-cost report to inspect actual installed files and
  compare it with recorded context receipts. Runtime cost claims still require
  comparable host or billing evidence.

## Residual Risks

- Static word counts approximate routing volume and do not prove model-token,
  latency, or monetary savings.
- A selective framework pack proves file and registered dependency closure; it
  does not prove that a target selected the right modules or project facts.
- Generated registries and deterministic checks validate structural contracts,
  not semantic correctness, architecture quality, or logical integrity.
- Existing targets may contain local deviations not visible in the source
  comparison and must preserve them during migration.
- Release-mode drift validation requires the prior `v0.1.0-alpha.9` tag. It
  cannot pass until that release tag exists and is reachable in Git history.
