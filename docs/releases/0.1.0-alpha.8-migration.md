## Adapter Contract Impact

- Framework, adapter schema, template, rule registry, rule ownership, target
  template, installer, routing, operation, validator, scaffold, bridge, and
  conformance surfaces changed.
- `ALATYR-TDD-001`, `ALATYR-EXTENSION-001`, and their rule-owner categories
  were added.
- `ALATYR-CONTEXT-001`, `ALATYR-SOURCE-001`, `ALATYR-RISK-001`,
  `ALATYR-INTEGRITY-001`, `ALATYR-CHANGE-001`, `ALATYR-ADAPTER-001`,
  `ALATYR-MODULE-001`, `ALATYR-OPERATION-001`, `ALATYR-BRIDGE-001`,
  `ALATYR-SAFETY-002`, `ALATYR-LIFECYCLE-001`, and
  `ALATYR-EVIDENCE-001` changed.
- The optional `test-first-development` module adds target policy assessment,
  explicit enablement, bounded recommendation, separate configuration and
  execution routes, RED/GREEN/refactor evidence, exceptions, and structural
  validation.
- The optional `extensions` module adds a declarative external package
  contract, offline inspection, compatibility and permission review,
  target-owned bindings, catalog/lock state, immutable source and installed-
  file evidence, explicit lifecycle, cross-assistant routing, and safe removal.
- Routine bootstrap does not load the full module. Static source measurement
  records 1,835 bootstrap words, a 67.4% reduction for the compact test-first
  route, and a 64.7% reduction for the compact extension route.

## Required Target Actions

- Run `recheck-after-framework-update` against this release.
- Migrate `.ai/alatyr.yaml` to adapter schema `7` and target template version
  `8` after reviewing target-local deviations and approval requirements.
- Add `ALATYR-TDD-001` and `framework/test-first-development.md` to the
  installed framework baseline even when the optional module remains deferred.
- Add `ALATYR-EXTENSION-001` and `framework/extensions.md` to the installed
  framework baseline even when extension lifecycle support remains deferred.
- Preserve existing test strategy, frameworks, commands, folders, fixtures,
  isolation, CI gates, merge rules, and historical test evidence. Do not
  replace them with source placeholders.
- Add the test-first intent, configuration flow, operation routing, and compact
  help aliases so `Alatyr enable test-first` can assess policy without treating
  the module as already enabled.
- Keep `test-first-development` deferred, disabled, not applicable, or blocked
  until a target owner and decision authority accept a resolved project policy.
- If the module is enabled, adapt its testing index, policy, execution flow,
  gate, evidence template, skill, manifest entries, module state, source-of-
  truth entry, help, bridge fields, and target validator coverage.
- Resolve modes, triggers, test levels, commands, isolation, exceptions,
  evidence requirements, review cadence, and known gaps from target evidence.
- Preserve existing external item provenance and installed files. When
  extension support is enabled, add the catalog, lock, intent, lifecycle flow,
  gate, review/lifecycle templates, module and manifest paths, operation/help
  aliases, bridge routing, source and prompt-injection policy, and validator
  coverage. Start catalog and lock empty unless target evidence proves an
  installed extension.
- Never convert an existing imported item into an active extension by
  inference. Inspect its package manifest or record the source as unresolved;
  resolve immutable revision and digest, license, compatibility, target
  bindings, permissions, approval, ownership, hashes, and validation before
  activation.
- Run the portable target adapter validator and target-selected tests or
  manual checks, or record each unavailable check and residual risk.
- Obtain target approval before adding dependencies, changing CI or merge
  requirements, changing protected policy, or enabling live external actions.

## Optional Target Actions

- Use advisory suggestions only when defect, invariant, contract, concurrency,
  risky-refactor, or recurring-regression evidence supports them.
- Keep suggestion mode off if the target does not want proactive test-first
  advice; explicit configuration and execution requests remain routable.
- Start with `regression-first` for reproducible defects or
  `characterization-first` for risky legacy refactors before considering
  strict TDD across broader target areas.
- Record justified `test-after-with-reason` exceptions when useful proof cannot
  precede implementation, instead of creating a low-value test.
- Use `Alatyr inspect extension <source>` for read-only review and `Alatyr
  suggest extensions <scope>` for bounded recommendation. Routine work must
  not search remote sources, install packages, or auto-update extensions.

## Residual Risks

- Structural validation cannot prove that a test assertion represents the
  intended business, architecture, data, security, or user contract.
- A recorded RED result does not prove expected-failure causality without
  assistant or human review of the failure reason.
- Poor target commands, fixtures, isolation, or ownership can make an enabled
  test-first workflow slow, flaky, or misleading.
- Proactive suggestions depend on changed-fact and risk classification and may
  miss target-specific triggers that are absent from the accepted policy.
- Assistant-native skill loading differs by client; canonical operation and
  context routing remain the portable baseline.
- Package and installed-lock validation cannot prove source trust, license
  interpretation, semantic quality, project suitability, or safe runtime
  behavior. Remote source access and executable dependencies remain governed
  by target policy and approval.
