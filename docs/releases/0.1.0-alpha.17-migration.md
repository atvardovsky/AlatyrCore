# Alatyr Release Migration Report

This reviewed report compares the nearest reachable tagged source baseline
`v0.1.0-alpha.3` with the source tree prepared for `0.1.0-alpha.17`.
Migration reports for intervening `0.1.0-alpha.4` through
`0.1.0-alpha.16` remain part of the evidence chain. This report is source
evidence, not authorization to modify, commit, publish, or operate a target
repository.

## Adapter Contract Impact

- Framework version changed because current-scope action authorization is now
  a portable core rule.
- Adapter schema version changed because the target manifest and operation
  catalog must route a structured action-authorization policy.
- Target template version changed because root instructions, gates, flows,
  request/output templates, bridge records, maturity surfaces, and lifecycle
  messages now apply the phase contract.
- Existing protected approval, allowed-action, tool-permission, team,
  delegation, mode, and validation controls remain independent boundaries and
  cannot grant a missing action phase.

## Required Target Actions

- Run `recheck-after-framework-update` in read-only mode before applying the
  migration.
- Record the current upgrade scope and separately authorized phases. Upgrade
  intent alone does not authorize commit, push, release, deployment, or
  another live action.
- Adapt the policy and companion surfaces without replacing target facts,
  permissions, approvals, actor authority, or stricter local safety rules.
- Validate that issue/backlog returns and ambiguous continuation remain
  read-only, prior completed-scope authorization expires, and subagents cannot
  broaden parent phases.
- Include `current_user_authorization` in final installation, update,
  recheck, and state-changing operation evidence.

- Add trustworthy conversation provenance to authorization evidence when the
  assistant surface exposes it; otherwise keep evidence explicitly

## Validation Run

Source validation: focused authorization, operation, manifest, target-
validator, generated-derivative, and release checks passed before the final
full validation pass.
Target validation: installed targets must run the portable adapter validator
and target-owned checks; source checks cannot prove interpretation of an
arbitrary conversation or compliance by a particular assistant client.

## Residual Risks

- Markdown and structural validation cannot force an assistant or client to
  honor user intent.
- Intent classification remains reasoning-dependent for ambiguous natural
  language; the safe fallback is inspection plus one bounded clarification.
- A target may have stricter authorization, authentication, protected-
  approval, or operational controls that still apply independently.
- Untrusted tools or automation outside the adapter can still mutate state if
  the surrounding platform grants them access.

## Safety

This report is evidence only. It does not modify a target, authorize an
assistant action, approve protected work, publish a tag, or claim that
