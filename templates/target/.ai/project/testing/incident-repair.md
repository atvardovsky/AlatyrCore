# Project Incident Repair

For uncertain or repeated defects in `{PROJECT_NAME}`, assess optional
`repair_review` with the target owner. Installed templates are not adoption;
preserve explicit disabled/deferred decisions. Schema 1 remains supported.
Explicit schema-2 adoption uses policy-owned assertions and digest-bound JSON
artifacts through `.ai/assistant/templates/repair-qualification.json`.

Retain the original case, competing hypotheses and fixture fidelity. Create the
reserved required `repair-evidence-review` obligation only after valid explicit
policy enablement. Unconfigured, disabled, deferred and core-only work uses
ordinary evidence-backed obligations, not implicit adoption. Preserve already
captured requirements; reconcile incompatible legacy captures with the owner
before further implementation, never erase them to obtain acceptance.
A faithful failing diagnostic may qualify repair, not functional acceptance.
Component success and faster measurements do not replace whole-flow acceptance.

Before retaining an experimental production change, record the incident-level
effect and reviewed retention/reversion reason in the existing repair evidence.
If local repairs repeatedly leave the original outcome unresolved, reassess
the owning invariant and cross-area mechanism rather than accumulating patches.
Keep current task/model bindings and unresolved predecessor references in the
existing task index; concurrent heads require explicit task selection.
Review bounded reusable lessons through the existing project-knowledge route;
recurrence suggests review, never automatic promotion or new authority.
