# Lifecycle Checkpoints

Load for installation hook setup or selected delivery/review, not every task.
Canonical rules remain in `.ai/framework/task-state-delivery.md`,
`.ai/framework/action-authorization.md` and `.ai/framework/session-continuity.md`.

1. Inspect the exact client/runtime, existing policy/definitions, trust and source
   locator. Before projection, run `lifecycle-checkpoint setup-plan` with explicit
   new/update identity. Existing settings, including disabled or absent update
   policy, remain unchanged without a separately scoped adoption decision.
2. New installs default to enabled procedural/observe delivery, unverified and
   reminder-free. Include supported project-local native setup in installation
   approval; only then select its provider. Policy/argv alone proves no callbacks.
   Never auto-trust, install plugins or change global settings.
3. Exercise harmless native event/denial/cancellation/timeout fixtures before
   recording exact client evidence. Unknown coverage means procedural fallback,
   not an enforcement claim. Recheck after client or definition changes.
4. Select hook delivery only for an existing registered task; small settled work
   keeps its ordinary lightweight path. At a new request/resume, review the task
   and newest authorized phases. Resume never clears interruption/end boundaries. Capture
   current context including the lifecycle policy, canonical active-task index,
   selected model/projection, descriptor and applicable result/contract/evidence
   files. A bind diagnostic names missing/changed selected inputs. Policy edits require renewed
   review and capture. Explicitly bind the current request via the portable
   delegate's `lifecycle-checkpoint` operation. The binding grants no authority.
   Adopted request guards require the brief in that baseline and
   `bind --request-brief <path>`; reconcile new request/resume IDs explicitly.
5. Before mutation, reconcile changed/expired selected context and check current
   approval, scope and permissions. After changes, review documentation and
   companion surfaces before rebinding. Review exposes separate evidence health;
   reconcile affected stale bindings, preserving read-only recovery and independent
   work. Use selective mutating-tool hooks only.
6. Before completion, inspect unresolved original outcomes and independent ready
   duties. Reminders remain zero by default and require separate adoption.
   They never execute work or replace canonical acceptance.
   A blocker, pause, interruption, completed scope or missing authority wins.
   For closed-task review, capture the actual closure, retained model and archived
   projection, then bind with `--completion-only`. This cannot permit pre-action
   execution. `completion-evidence-consistent` means canonical selected records
   agree, not task acceptance or current runtime readiness. Empty ready lists,
   provisional evidence and component passes do not establish completion.
   Preserve the full request inventory across supporting scopes/publication.
   Partial answers retain every remaining outcome; preparation is not delivery.
7. Report configured/adopted/exercised/intercepted states separately. Keep native
   errors, missing coverage and procedural checks visible. Never infer success
   from a configuration file or validator result alone.

`lifecycle-checkpoint review --request-brief <path>` checks stdin action JSON
without writes/adoption. See the operator guide for actual-action mappings,
partial-answer/completion distinctions and client-verification limits.
Optional schema-2 delivery controls use
`.ai/framework/test-execution-selection.md#bounded-delivery-review`; retain the
selected validation history in the baseline, without enabling controls on update.
Costly/repeated work may explicitly adopt
`.ai/framework/test-execution-selection.md#delivery-efficiency`: retain schema-2
history, its predecessor, progress and run receipts in the same baseline.
Report adoption, exercised review and native interception separately; exhausted
budgets preserve read-only recovery, original outcomes and every required gate.
Opt-in schema-3 focus: `.ai/framework/task-state-delivery.md#request-bound-work`.
Optional `terminal_control` uses the same brief and canonical command receipts;
see `.ai/framework/task-state-delivery.md#terminal-action-prerequisites`.
Bind exact candidate/environment evidence, require terminal success before each
dependent mutation, and retain the original action brief digest. Refresh receipt
selection after a retry, not history or policy. A session ID is not a pass.
Before material/recurring repair plans, capture source-derived brief outcomes/surfaces
with `.ai/assistant/templates/problem-model.json` in the existing model. Use
`.ai/framework/task-state-delivery.md#outcome-qualification`; disclose absent
adoption and native-interception limits.

Runtime session state stays ignored under `.ai/.runtime/lifecycle-hooks/` and
contains no conversation, approval record or duplicate project task inventory.
